# 验收：什么信号可信，什么信号会骗你

这份文档存在的唯一理由：**我今天信了几个不该信的信号，导致"验证通过"但实际没生效。**

---

## 核心纪律

> **"执行过动作" ≠ "成功"。**
>
> 打开弹窗不算数、上传返回成功不算数、下拉列表里出现目标文本不算数。
> **只有平台自己吐出的、绑定了这次操作的回执才算数。**

---

## ❌ 不可信的信号

| 信号 | 为什么骗人 |
|---|---|
| `bsk upload` 返回 `{"file_names":[...]}` | 只说明"动作执行了"，文件是否被页面接受是另一回事 |
| 弹窗里的 canvas / 中间预览 | 平台还没接受，只是本地渲染 |
| **下拉选项列表里出现目标文本** | 选项**永远**在那里，与你选没选无关 |
| `document.body.innerText` 包含某关键词 | 可能来自选项列表、推荐位、预览区 |
| 手机预览镜像里的图 | 是镜像，不是主卡片 |
| 元素"看起来有图" | 可能是平台自动生成的默认图 |

### 🔴 我实际栽过的坑

**视频号的视频标注**：我读到页面里有 `含AI生成内容` 就判定成功。
但那个文本来自**下拉选项列表**。正确信号是**按钮本身从占位符变成了选中值**：

```
❌ 错误信号： 页面文本里有 "含AI生成内容"
✅ 正确信号： @e button "选择视频标注"   →   @e button "含AI生成内容"
                                  ↑ 占位符            ↑ 选中值
```

**规律：下拉/选择类字段，看控件的文本是不是从「占位符」变成了「值」。**

## ✅ 可信的信号（按字段类型）

### 标题 / 文本类

```js
document.querySelector('<标题选择器>')?.value === '期望的标题'
```

**必须回读，不能只看填写动作的返回。**

### 话题实体

| 平台 | 判定 |
|---|---|
| 小红书 | `a.tiptap-topic` 的 `data-topic` JSON 里的 `name` |
| 抖音 | `[data-mention="#"]` 节点 |
| B站 | `.label-item-v2-content` 的文本 |
| 视频号 | `span.hl.topic` |

**并要求：每个请求的话题都存在实体，且没有残留纯文本。**

### 下拉/选择类（声明、分区）

**看控件自身的文本**：

```
小红书：[...document.querySelectorAll('.d-select')][0].innerText  → "笔记含AI合成内容"
抖音：  document.querySelector('.selectBox-buZRzi').innerText      → "内容由AI生成"
B站：   document.querySelector('input.bcc-select-input-inner').value → "含AI生成内容"
视频号：button 的文本从 "选择视频标注" 变成 "含AI生成内容"
```

### 封面 —— 必须拿到「平台接受后的 URL」

| 平台 | 回执 |
|---|---|
| **小红书** | `ros-preview.xhscdn.com` 的 URL |
| **B站** | `.cover-img` 的 `archive.biliimg.com` / `biliimg.com` URL |
| **抖音** | **竖版和横版必须得到两个不同的接受 URL** |
| **视频号** | 主卡片 `.vertical-cover-wrap img` / `.horizon-cover-wrap img` 的 URL，**两个都要变** |

**⚠️ 判断"真的变了"要和操作前的 URL 对比。**
今天 B站 修封面时，就是靠 URL 从 `2d01435f...` 变成 `70b1e7ab...` 才确认成功的。

**⚠️ 同一张图传给两个槽会得到相同 URL —— 那是错的。** 两个槽必须是不同的文件。

### 视频上传

**完成证据**：

```
✅ 出现「重新上传」「更换视频」「上传完成」
✅ 抖音：出现 video 元素
✅ B站：页面文本含「上传完成」

❌ 仍在进行的信号：
   上传中 / 百分比 / 取消上传 / 转码中 / 处理中
```

**⚠️ 预览卡片可能在传完之前就出现**（视频号实测在 50% 就有封面卡片了）。**那只说明在上传，不等于传完。**

## 平台加载慢的字段

| 平台 | 现象 | 应对 |
|---|---|---|
| 小红书 | 话题建议面板**出现得慢**，且会重渲染 | 轮询快照，拿 ref 再点 |
| 小红书 | 4K / 大视频时封面编辑器报「视频加载遇到问题」 | 用它的官方退路「回退到旧版封面编辑弹窗」 |
| 视频号 | 上传期间字段**锁定**（「文件上传中，请等待完成后再编辑」） | 必须等传完 |
| 抖音 | `#添加话题` 按钮 ref 会变 | 每次重新解析 ref |

## 记录本次操作前状态的纪律

**任何"修改"类操作，都要在动手前先记录基线：**

```
封面类  → 记录操作前的封面 URL（用于事后对比是否真的变了）
下拉类  → 记录操作前的控件文本
话题类  → 记录操作前已有的实体列表
```

**没有基线，就没有"变了"这个结论。**

## 幂等性

**重跑同一条流程时，必须先判断状态，不能无脑重放。**

实测（小红书）：上传中重复注入同一文件 → 平台静默忽略，不产生重复上传。

**但这只是小红书的实测。其他三家未知，所以必须自己做守卫。**

推荐三态判定：

```
already_ready    目标本来就完成了     → 什么都不做
resume_existing  目标正在上传中       → 只等待，不重新注入
injected         这次是我注入的       → 正常流程
```

> 来自 oil-oil 的 `platform-common.md`：
> *"重启后，`resume_existing` 是上传**没有**被重复注入的必需证据。"*
> 即：**系统要能证明自己没干重复的事**，而不是等出问题再发现。

## 最终交付前

**"停在发布按钮前"的定义：**

```
✅ 最终发布按钮可见、可点、且未被点击
✅ 所有字段的实体/回执都能在当前页面复现
✅ 没有阻塞性弹窗
❌ 不能声称"已发布"
```

`READY` ≠ 已发布。**最终必须由人工过一遍再点发布。**
